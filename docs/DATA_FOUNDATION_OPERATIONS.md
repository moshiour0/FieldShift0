# Data Foundation Operations

This runbook covers the first reproducible archive milestone: NASA POWER daily point history for the nine configured Bangladesh reference points. It does not claim official AEZ zonal coverage, farm-level measurements, or satellite-product coverage.

## What the backfill produces

The manual GitHub Actions workflow is named **Backfill nine-region NASA POWER daily history**. It defaults to completed calendar years 2016–2025 and processes the nine configured points in groups of at most three concurrent region jobs.

Each accepted year is stored as:

`power-history/{region_id}/{year}.json`

The archive is generated by `scripts/prefetch_history.py` and `fieldshift.v3.history.prefetch_year`. A year is written only after the NASA POWER response passes date completeness, parameter finiteness, physical-bound, provenance and checksum checks. Existing checksum-valid objects are reused on a rerun; the workflow does not pass `--refresh`, so a successful year is not fetched again just because another year failed.

The source is NASA POWER Daily API at the configured representative latitude/longitude, using local solar time (LST). These are gridded-point samples, not field sensors, district averages, official AEZ means, or farm-specific observations. The current adapter permits only bounded gap interpolation according to `FIELD_SHIFT_POWER_MAX_IMPUTE_FRACTION` and `FIELD_SHIFT_POWER_MAX_GAP_DAYS`; source metadata marks imputed values. A year that exceeds those quality limits fails rather than being silently filled with zeros.

The existing Mymensingh 2016–2025 monthly aggregate remains a separate chart-only product. It is not converted into daily records or accepted by the crop-model daily archive reader.

## Required GitHub configuration

Before dispatching the workflow, create these **repository Variables** in GitHub (not source-code constants):

| Variable | Required | Purpose |
|---|---:|---|
| `FIELD_SHIFT_ARCHIVE_S3_BUCKET` | Yes | Destination S3 bucket |
| `AWS_ROLE_ARN` | Yes | IAM role assumed through GitHub OIDC |
| `AWS_REGION` | No | Defaults to `ap-southeast-1` |

The AWS role trust policy must accept GitHub's OIDC token for this exact repository and the branch/ref from which the manual workflow is dispatched. Do not use a broad wildcard subject when a branch-scoped trust condition is possible.

Grant the role only the actions required for this archive prefix: `s3:GetObject` and `s3:PutObject` on `arn:aws:s3:::BUCKET_NAME/power-history/*`. The workflow does not need account-wide S3 permissions. The script writes objects with server-side AES-256 encryption.

The preflight job verifies the bucket and role variables and validates the requested year window before any NASA request begins. If either required variable is missing, the workflow fails with an explicit message and does not start ingestion.

## Run and resume

1. Open GitHub Actions and select **Backfill nine-region NASA POWER daily history**.
2. Dispatch with start year 2016 and end year 2025 for the intended initial historical range. Only completed years are accepted.
3. Review each of the nine region jobs. A failed region/year makes that region job fail; other region jobs continue.
4. Correct the provider, IAM, or storage issue and rerun the same year window. Checksum-valid S3 year files are skipped; only missing or invalid years need a new fetch.

Do not use `--refresh` for a routine recovery. That option deliberately bypasses the archive reuse path and re-requests already archived years.

## Runtime access is a separate prerequisite

A successful GitHub upload does not by itself make the archive visible to the Vercel API. The FieldShift runtime also needs:

- `FIELD_SHIFT_ARCHIVE_S3_BUCKET` in the Vercel environment; and
- an application-side AWS credential chain with read-only `s3:GetObject` access to `power-history/*`.

The GitHub Actions OIDC write role is not automatically available inside Vercel. Configure a separate least-privilege runtime identity using a Vercel-supported credential mechanism. Do not copy write credentials into the repository or browser environment. Until Vercel can read and checksum-validate the objects, the API must continue to report history as unavailable rather than implying that ingestion has been published.

The durable refresh queue is separate from the object archive. `FIELD_SHIFT_JOBS_DSN` must point to a PostgreSQL database before `POST /api/refresh-jobs` can be treated as durable. A Vercel `/tmp` SQLite file or Python process memory is not durable across serverless instances. Do not attach this project to an unrelated Supabase database merely because another project is available in the account.

## Verify the published archive

After the GitHub run succeeds and Vercel runtime read access is configured, verify each region through:

`GET /api/history/{region_id}?start_year=2016&end_year=2025`

For a complete daily archive, confirm all of the following in the response:

- `status` is `complete`;
- `archive_representation` is `daily`;
- `missing_years` is empty;
- each annual row has `days == expected_days` and `archive_representation == daily`.

Also check `GET /api/data-status/{region_id}`. An HTTP 200 response alone is not proof of complete coverage; inspect the returned status and provenance. Check `GET /api/status` for configuration presence, but remember that configuration presence does not independently prove live AWS or NASA connectivity.

## Scope boundaries

This workflow ingests NASA POWER only. It does not download or validate SMAP, MODIS MOD16, HLS, or GPM archives. It does not add official BARC/BAMIS AEZ boundaries or a spatial crosswalk. The nine points remain representative samples. Crop/soil recommendations remain a Mymensingh pilot until locally calibrated against Bangladesh field observations.
